# Budget Management 룰 명세

> **NDS 전용 명세** (upstream 대상 아님). 팀 → 유저 → 앱 3계층 예산 모델의
> 비즈니스 룰을 정의합니다. 구현은 별도 작업으로 진행하며, 이 문서가 기준입니다.
>
> 상태: **확정안 v6.1** (구현 전, 2026-09-29)
>
> **v6 → v6.1 변경 요약 — 리뷰 보강 (규칙 변경 없음, 공백 메움)**
> - `X-Budget-Remaining` 정의 명확화: **차단 시점까지의 잔여**(SOFT_WARNING이면 1.10×limit 기준) — §6-5
> - `T`의 의미 정정: "하드 상한"은 HARD_BLOCK에서만 — §1
> - **팀 삭제** 처리 추가: Cognito stale-team 정리를 포함한 모든 팀 소멸은 멤버별 §4-5 이관과 동일 처리 — §4-7
> - **유저 비활성화/삭제** 처리 추가: 예산 config 보존, 인증 단계가 먼저 차단 — §4-7
> - 팀 config 행은 `T = null`이어도 생성 가능함을 명시 — §3-1
> - `confirm=true` 재요청도 별도 audit action으로 기록 — §3-0
> - `no_team_assigned`는 degenerate case 방어 장치로 위치 정리(실측 dev DB: team_id NULL 0건, 모든 생성 경로가 DEFAULT_TEAM_ID 폴백) — §4-6
> - D-19 데이터 점검 목록에 `team_id IS NULL` 항목 추가(정보용, 현재 0건)
>
> **v5 → v6 변경 요약 — 예약(POOL) 모델 폐기, CAP 모델 채택**
> - 유저 예산 `A_u`는 풀에서 떼어내는 **예약이 아니라 개인 상한(cap)**. `ΣA_u > T`(초과 약정) 허용 — §1·§2
> - 미설정 유저에게는 팀 단위 **기본 cap `D`**를 적용 → 풀 선착순 독점 문제 해결 — §3·§4
> - 폐지: 잔여 풀 `P`, `pool_used` 카운터, 예약 보장 조건 G, `ΣA ≤ T` 불변식, 팀 감액 거부,
>   팀 삭제 거부, 팀 단위 잠금/버전, 유저×팀×월 카운터 키 변경, `pool_*` 에러 코드
> - 균등분배 = N건 bulk 쓰기가 아니라 **`D = floor_cent(T/N)` 계산 도우미** — §4-4
> - 유지(v5 결정): `null`/`0` 의미, 정책 판정 경계값, 초과 허용 오차, 확인 필요 경고, 팀 이동·팀 없는 유저 처리,
>   리더 본인 설정 금지, 클라이언트 식별 신뢰 수준, 에러 코드·헤더, 캐시 TTL, DEVELOPER 노출 범위, Downgrade 정의

## 0. 용어

| 기호 | 의미 |
|---|---|
| `T` | 팀 예산 (월간 하드 상한, USD). `null` = 미설정 → 팀 전원 차단 |
| `D` | 팀 기본 유저 cap (`default_user_cap`). `A_u`가 없는 멤버에게 적용. `null` = 기본 cap 없음(팀 한도 `T`만 적용), `0` = 미설정 유저 차단 |
| `A_u` | 유저 u의 개인 cap. `null` = 미설정(→ `D` 적용), `0` = 명시적 차단 |
| `cap_u` | 유저 u의 실효 개인 cap = `A_u ?? D` (`A_u`가 `null`이면 `D`, 둘 다 `null`이면 개인 cap 없음) |
| `app_c` | 유저의 클라이언트별 cap (`claude-code` / `cowork` / `codex`). `null` = 미설정, `0` = 해당 앱 차단 |
| `used_u` | 유저 u의 해당 월 사용액 (**유저×월**, 팀과 무관하게 유저를 따라감) |
| `team_used` | 해당 팀에 귀속된 해당 월 사용액 (요청 시점의 소속 팀에 귀속) |
| `app_used` | 유저 u의 해당 앱·해당 월 사용액 (앱 cap 설정 여부와 무관하게 항상 집계 — 현행) |
| 초과 약정률 | `(ΣA_u + D × N_미설정) / T` — **정보 표시용 지표**, 강제하지 않음 (`D = null`이면 표시 생략) |
| 월(period) | KST 기준 `YYYY-MM` |

- 금액 정밀도: 예산 입력·저장은 **$0.01(센트) 단위**(DB `Numeric(12,4)`에 저장하되 소수 2자리 초과 입력은 거부).
  사용액은 소수 6자리(`Numeric(12,6)`)로 누적. 비교는 Decimal로 수행.

## 1. 계층 모델

```
TEAM (T)  ── 팀 전체 월간 총량 통제. 유일한 "돈의 총량" 기준
 └─ USER (cap_u = A_u ?? D) ── 개인 상한 (예약 아님, 합계가 T를 넘어도 됨)
     └─ APP (app_c) ── A_u 내부의 앱별 개별 cap (예약 아님, 앱끼리 A_u 공유)
```

> ⚠️ `T`가 실제 "하드 차단"인지는 **팀 정책에 따른다** — `HARD_BLOCK`이면 100% 차단,
> `SOFT_WARNING`이면 110%까지 허용, `THROTTLE`이면 금액 차단 없이 경보 기준선이 된다(§6-2).
> 팀 총액을 하드하게 막으려면 팀 정책은 `HARD_BLOCK`이어야 한다.

- **CAP 모델.** 모든 계층은 "여기까지만 쓸 수 있다"는 상한이며, 누구에게도 사용을 **보장하지 않는다**.
  모든 유저는 자기 `cap_u`와 팀 잔액(`T - team_used`) 중 먼저 닿는 쪽에서 멈춘다.
- **초과 약정(overcommit) 허용.** `ΣA_u > T`여도 된다. 전원이 동시에 cap까지 쓰지 않는다는 전제로
  활용률을 높이는 것이 목적이며, 팀 총액은 `T`가 항상 막는다.
- **공정성은 `D`로 확보.** `D`를 설정하면 미설정 유저 한 명이 팀 예산을 독점할 수 없다.
  `D = null`이면 미설정 유저는 `T`만 적용받는다(현행 pass-through와 동일, 선착순).
- 카디널리티: **유저는 최대 1개 팀에만 소속**된다. 다중 팀 소속은 지원하지 않는다.

## 2. 불변식 (항상 참이어야 함 — 설정값 기준)

| # | 규칙 |
|---|---|
| I-1 | `T`, `D`, `A_u`, `app_c`는 `null` 또는 `≥ 0`, 센트 단위. `null` = 미설정, `0` = 명시적 차단 (정책 무관) |
| I-2 | 각 앱에 대해 `app_c ≤ A_u` (개별 비교). `Σapp_c`는 `A_u`를 초과할 수 있다 |
| I-3 | `app_c ≠ null`이면 `A_u ≠ null` (부모 유저 예산 필수, `D`로는 불충분). 유저 예산 삭제 시 앱 예산은 **cascade 삭제** |
| I-4 | `A_u`·`app_c`는 해당 팀 **현재 멤버**에게만 존재 가능 (팀 소속 검증 — 모든 쓰기 경로) |

- **팀↔유저 간 합계 불변식은 없다.** `ΣA_u ≤ T`, `A_u ≤ T`, `D ≤ T` 모두 강제하지 않는다
  (`A_u > T` 또는 `D > T`는 저장 가능하되 UI에서 "팀 예산이 먼저 적용됩니다" 안내).
  그 결과 `T` 감액·삭제, 팀 이동이 어떤 불변식도 깰 수 없다.
- 불변식은 **설정값**에 대한 것이다. 사용량이 한도를 넘는 상태(`used ≥ limit`)는 위반이 아니다(§6-4).
- 모든 쓰기 경로(`set_user_budget`, `allocate`, 앱 예산 변경, 팀 이동)는 **단일 공통 검증 함수**를 통과한다.

## 3. 팀 예산 규칙

### 3-0. 공통 — 거부 vs 확인 필요 경고, 동시성

- **거부**: 불변식·권한 위반. HTTP 403/409/422 + 코드(§6-5). 우회 불가.
- **확인 필요 경고**: 불변식은 지키지만 저장 즉시 차단을 일으키는 변경.
  서버가 `409 confirmation_required` + 영향 내역을 반환하고, 클라이언트가 `confirm=true`로 재요청해야 반영.
  (UI 경고만으로 두지 않는다 — API 직접 호출도 동일.)
  `confirm=true`로 확인된 반영은 **일반 변경과 구분되는 audit action**(예: `..._CONFIRMED`)으로 기록해
  "경고를 본 뒤 강행"임을 추적 가능하게 한다.
- **동시성**: 팀↔유저 간 합계 제약이 없으므로 팀 단위 잠금은 필요 없다.
  - `T`·`D`: 팀 예산 행 단일 필드 갱신, last-write-wins + 감사 로그.
  - `A_u`와 `app_c`(I-2): 같은 유저의 두 값이 엮이므로 **유저 예산 행을 `SELECT … FOR UPDATE`로 잠근 트랜잭션** 안에서 검증·쓰기.
- 캐시 반영은 **커밋 이후** 수행(§6-6). 커밋 실패 시 캐시는 건드리지 않는다.

### 3-1. `T` 설정/수정/삭제 — ADMIN 전용

- 모드 선택 UI 없음(CAP 고정). 화면에 `T`, `team_used`, `D`, 초과 약정률 표시.
- **증액**: 항상 허용.
- **감액**: 항상 허용. `team_used ≥ T_new`이면 **확인 필요** — "현재 사용량이 새 예산 이상이므로 팀 전원이 즉시 차단됩니다".
  유저 cap(`A_u`, `D`)은 건드리지 않는다.
- **삭제(해제)**: 항상 허용, **확인 필요** — "팀 전원이 `team_budget_unset`으로 차단됩니다".
  `A_u`·`app_c`·`D`는 **보존**되며 `T` 재설정 시 그대로 다시 적용된다.
- `T = null` 상태에서도 `D`·`A_u`·`app_c` 설정은 허용(사전 준비 용도). 요청은 `team_budget_unset`으로 차단.
- 팀 config 행은 **`T`가 null이어도 생성 가능**하다 — "행 없음"과 "`T=null`인 행" 모두 `team_budget_unset`으로
  동일하게 판정되며, `D`는 `T`와 무관하게 이 행에 저장된다.

### 3-2. `D`(기본 유저 cap) 설정/수정/삭제 — ADMIN 전용

- `D`는 미설정 멤버 전원(TEAM_LEADER 포함)에게 적용되므로, 리더 본인 cap 결정권 문제(§4-1)를 피하기 위해 ADMIN 전용.
- 감액 시 `used_u ≥ D_new`인 미설정 멤버가 있으면 **확인 필요** — "미설정 유저 N명이 즉시 차단됩니다" + 명단.
- `D = 0` 설정 시 **확인 필요** — "개인 예산이 없는 멤버 N명이 모두 차단됩니다".
- 삭제(`null`) = 미설정 유저는 `T`만 적용(선착순). UI에서 "한 명이 팀 예산을 모두 쓸 수 있습니다" 안내.

## 4. 유저 예산 규칙

### 4-1. 설정/수정/삭제 — ADMIN + TEAM_LEADER(자기 팀, 본인 제외)

- TEAM_LEADER는 **본인의 `A_u`·`app_c`를 설정/수정/삭제할 수 없다** → `403 self_allocation_forbidden`
  (이해상충 방지). 리더 본인 예산은 ADMIN이 관리한다(미설정이면 `D` 적용).
- 한 번에 한 명씩 변경.
- **입력 상한 없음** (초과 약정 허용). UI에는 참고값으로 `T`, `D`, 현재 초과 약정률, 입력 후 예상 초과 약정률을 표시.
  `A_u > T`이면 "팀 예산이 먼저 적용됩니다" 안내(저장은 허용).
- 팀 소속이 아닌 유저에 대한 설정은 **거부** `403 user_not_in_team` (I-4).
- `0` 입력 = 차단. 빈 값 = 삭제(→ `D` 적용). UI에서 두 동작을 구분해 표시.

### 4-2. 변경 시 검증·경고

- `A_u_new < max(app_c)` → **거부** `user_budget_below_app_cap` — "앱 예산(앱명 $X)이 새 유저 예산을 초과합니다. 먼저 앱 예산을 줄이세요." (I-2)
- `A_u_new ≤ used_u` → **확인 필요** — "현재 사용액($X)이 새 예산 이상이므로 즉시 차단됩니다".
- 삭제(→ `D` 적용) 시 `D ≠ null`이고 `used_u ≥ D`이면 **확인 필요** — "기본 cap($D) 적용으로 즉시 차단됩니다".
- 삭제 시 앱 예산은 cascade 삭제(I-3). 확인 창에 삭제될 앱 예산 목록 표시.

### 4-3. 월 중 변경과 사용량

- `used_u`는 유저×월로 누적되며 cap의 출처(`A_u`/`D`)가 바뀌어도 그대로 유지된다.
  월 중 cap 변경·삭제·설정은 **즉시 이번 달 누적 `used_u`에 대해** 판정된다.
- 앱 cap을 월 중에 새로 만들면 이미 누적된 `app_used`가 즉시 계산된다(현행 동작).

### 4-4. 균등분배 — ADMIN 전용, `D` 계산 도우미

- 균등분배는 더 이상 N명에게 예약을 쓰는 bulk 액션이 아니다. **`D = floor_cent(T / N)`을 계산해 `D`를 설정**하는 UI 도우미이며,
  실제 쓰기는 §3-2의 `D` 설정 API 하나다(권한도 동일하게 서버에서 ADMIN 강제).
- N = 해당 팀의 **활성 현재 멤버 전원**(TEAM_LEADER 포함, `A_u` 설정 유저 포함).
- 옵션 "개별 설정 초기화": 체크 시 같은 트랜잭션에서 팀 멤버 전원의 `A_u`(및 cascade `app_c`)를 삭제해 전원이 `D`를 쓰게 한다.
  확인 창에 삭제될 개별 예산 목록 표시. 미체크 시 기존 `A_u`는 유지(→ 초과 약정률이 1을 넘을 수 있음, 화면에 표시).
- `T = null`, N = 0, 또는 `floor_cent(T/N) = $0.00`이면 **거부** `equal_split_nothing_to_allocate`.
- 멤버 수가 바뀌어도 `D`는 자동 재계산되지 않는다(신규 멤버는 합류 즉시 기존 `D` 적용).

### 4-5. 팀 이동 — ADMIN 전용

유저를 팀 X → 팀 Y로 옮길 때, 단일 트랜잭션에서:

1. 팀 X에서 설정된 `A_u`와 모든 `app_c`를 **삭제**한다(팀 X 관리자가 정한 값이므로 따라가지 않음).
2. 팀 Y에서는 미설정으로 시작 → 팀 Y의 `D` 적용. 필요하면 팀 Y 관리자가 `A_u`를 새로 설정.
3. **사용량 귀속**:
   - `team_used`: 이동 전 사용액은 **발생한 팀 X에 남는다**(요청 시점 소속 팀에 귀속 — 현행 키 구조). 팀 Y의 `team_used`에는 포함되지 않는다.
   - `used_u`: **유저를 따라간다**. 팀 Y의 개인 cap은 이번 달 전체 사용액(팀 X 사용분 포함)에 대해 판정된다.
     → 팀을 옮겨 개인 한도를 초기화하는 우회가 불가능하다.
   - `app_used`: 유저를 따라간다(`used_u`와 동일).
4. 이동 시점에 `used_u ≥ cap_u(Y)`이면 **확인 필요** — "이동 즉시 개인 한도로 차단됩니다".
5. 팀 Y가 `T = null`이면 이동은 허용되며 해당 유저는 `team_budget_unset`으로 차단된다.
6. 유저 config 캐시 무효화(§6-6). 팀 config는 변하지 않는다(`T`, `D`는 팀 속성).

- 합계 불변식이 없으므로 이동은 어떤 불변식도 깰 수 없다.

### 4-6. 팀 없는 유저

- `team_id = null` 유저의 요청은 **fail-closed**: 예산 검사 이전에 `429 no_team_assigned`로 차단.
- 팀 없는 유저에게는 `A_u`·`app_c`를 설정할 수 없다(I-4).
- 실제로는 모든 유저 생성 경로가 팀을 강제 배정한다 — Cognito sync(그룹 미매칭 시 `DEFAULT_TEAM_ID` 폴백),
  OIDC 자동 프로비전(`OIDC_REJECT_UNMATCHED_GROUPS`면 거부, 아니면 `DEFAULT_TEAM_ID`),
  stale 팀 정리(멤버 전원 default 팀 이동). dev DB 실측 `team_id IS NULL` 0건 (2026-09-29).
  이 규칙은 config 오설정(`DEFAULT_TEAM_ID` 공백)이나 수동 DB 조작 같은 **degenerate case 방어 장치**다.

### 4-7. 팀 삭제 · 유저 비활성화

- **팀 삭제**(수동 삭제 또는 Cognito sync의 stale-team 정리로 팀이 소멸): 모든 경로에서 멤버는 다른 팀
  (sync 정리의 경우 `DEFAULT_TEAM_ID`)으로 이동하며, 각 멤버는 **§4-5 팀 이동과 동일하게** 처리된다 —
  즉 옛 팀의 `A_u`·`app_c`는 삭제되고 새 팀의 `D`가 적용된다. 예산 행이 orphan으로 남는 경로를 만들지 않는다.
- **유저 비활성화/삭제**(`is_active=false` 또는 hard delete): 해당 유저의 `A_u`·`app_c`는 **보존**한다.
  비활성 유저는 VK 인증 단계에서 이미 차단되므로 예산 검사에 도달하지 않으며, 재활성화 시
  기존 예산 설정이 그대로 이어진다. 카운터(`used_u`·`app_used`)도 유지 — 비활성화로 한도를 초기화하는
  우회를 막는다.

## 5. 앱별 예산 규칙

- `app_c` = 유저 예산 `A_u` 안의 **개별 cap** (다른 앱·미설정 앱과 `A_u`를 공유)
- **I-2 강제: 각 `app_c ≤ A_u`**. 합계 제약은 없다.
  - 예: `A_u=$3`, `claude-code=$3`, `cowork=$1` → 허용. 사용은 합산 `$3` 이내, 그중 cowork는 `$1` 이내.
- UI 입력 상한 = `A_u` (모든 앱 동일). 초과 입력은 **거부** `app_cap_exceeds_user_budget`
- `app_c = 0` = 해당 앱 차단. 빈 값 = 삭제(개별 cap 없음).
- **미설정 앱** = 개별 cap 없이 `cap_u`까지 사용 가능. 모든 앱 사용량은 `used_u`에 합산.
- `A_u = null`(`D`를 쓰는 유저 포함)에게는 앱 예산을 만들 수 없다(I-3) → **거부** `app_budget_requires_user_budget`.
  앱 cap이 필요하면 먼저 `A_u`를 설정한다.
- `app_c_new ≤ app_used`면 **확인 필요** — "해당 앱 즉시 차단".

### 5-1. 클라이언트 식별과 신뢰 수준

- 식별: gateway-proxy `client_identifier`가 요청 헤더(`User-Agent`, `anthropic-client-platform`, `originator`)로
  `claude-code` / `cowork` / `codex` / `other`를 판정한다. 이 헤더는 **클라이언트 자기 신고값이며 위조 가능**하다.
- 따라서 **앱 cap은 보안 경계가 아니라 사용량 배분 장치**다. 위조로 할 수 있는 것은 `A_u` 안에서 앱 간 사용량을
  옮기는 것뿐이며, `cap_u`·`T` 한도는 VK(가상 키) 신원 기준이라 우회되지 않는다.
- 알 수 없는 클라이언트(`other`): 앱 cap 대상이 아니며(설정 불가), 유저·팀 단계에만 집계·집행된다.
  `other`로 위장해 앱 cap을 피하는 것을 막으려면 기존 `allowed_clients` 허용 목록에서 `other`를 제외한다
  (인가 축은 VK + 팀 + `allowed_clients`).

## 6. Enforcement (요청 시점, gateway-proxy)

### 6-1. 검사 순서

요청당 아래 순서로 평가한다. **차단 판정이 나온 첫 단계**의 코드로 429를 반환한다.
경고·throttle은 모든 단계를 끝까지 평가해 합친다(§6-3).

0. **팀 소속**: `team_id = null` → `no_team_assigned`
1. **팀 설정**: `T = null` → `team_budget_unset`
2. **유저 단계**: `cap_u ≠ null`이면 `used_u` vs `cap_u`
   - 정책: `A_u`가 있으면 유저 예산 행의 정책, `D`를 쓰면 **팀 예산 정책**
   - `cap_u = null`(`A_u`·`D` 모두 미설정)이면 이 단계 생략
3. **팀 단계**: `team_used` vs `T` (정책 = 팀 예산 정책). **모든 유저에게 항상 적용**
4. **앱 단계**: 식별된 client에 `app_c ≠ null`이면 `app_used` vs `app_c` (정책 = 앱 예산 행의 정책)

### 6-2. 정책별 판정 (계층마다 독립 적용, `limit` = 해당 계층 한도)

| 정책 | 허용 | 허용 + 경고 | 차단 |
|---|---|---|---|
| `HARD_BLOCK` | `used < limit` | — | `used ≥ limit` → `<tier>_budget_exceeded` |
| `SOFT_WARNING` | `used < limit` | `limit ≤ used < limit × 1.10` | `used ≥ limit × 1.10` → `<tier>_soft_limit_exceeded` |
| `THROTTLE` | 항상 (금액 차단 없음) | `used ≥ limit × 0.80`이면 throttle 활성: 유저 RPM을 `throttle_rpm_pct`(기본 50%)로 감경 | 없음 |

- `limit = 0`은 **정책과 무관하게 항상 차단**(I-1의 "명시적 차단"). 현행 Lua/`_evaluate_layer`의 `limit > 0` 분기로 인해
  SOFT/THROTTLE에서 0이 통과되는 동작은 변경 대상(D-8).
- SOFT_WARNING의 `1.10`은 `soft_limit_pct`(기본 110). 팀 정책이 THROTTLE이면 `T`는 금액 상한이 아니라
  경보 기준선이 된다 — 팀 총액을 하드하게 막으려면 팀 정책은 HARD_BLOCK이어야 한다.

### 6-3. 결과 조합

- 차단: 첫 차단 단계(0→4 순)의 코드 하나만 반환.
- 경고: 경고 상태인 계층을 모두 모아 헤더로 반환(§6-5).
- throttle: 활성 계층이 여럿이면 **가장 작은 `throttle_rpm_pct`**를 적용. (현행은 팀 결과만 반영 → D-12)

### 6-4. 초과 허용 오차 · 카운터 일관성 모델

- **사전 검사 + 사후 차감**만 사용한다. 추정 비용 선점(pre-hold)은 하지 않는다(스트리밍 응답은 종료 전 비용 미확정, §10).
- 결과적으로 한도 직전의 요청은 한도를 넘겨 완료될 수 있고, 동시 요청은 같은 잔액을 보고 함께 통과할 수 있다.
  **계층당 최대 초과 ≈ 한도 통과 시점의 in-flight 요청 비용 합**이며 보장된 상한은 없다.
  완화 장치는 유저 RPM/CPM rate limit. 보고 화면에서 `used > limit`은 정상 상태로 표시한다.
- 차감: 응답 완료 후 실제 비용 `c`를 `used_u`, `team_used`(요청 시점 팀), 식별된 앱의 `app_used`에 각각 원자적으로 가산
  (`INCRBYFLOAT`, **현행 키 구조 유지**: `budget:user:{uid}:{period}`, `budget:team:{tid}:{period}`,
  `budget:user:{uid}:{client}:{period}`). 비용 산정 단가는 **요청 시작 시점에 유효한 단가 버전**.
- 계층 간 평가는 원자적이지 않다(키 slot이 다름 — 허용). 각 키 단위로만 원자적.
- 정합성: Redis 카운터 = 집행용, `usage_logs` = 원장(source of truth). 키 유실 시 DB에서 복원(현행 안전망).
  Redis 장애 시 DB 폴백도 동일 규칙·동일 경계값으로 판정한다.
- 임계값 알림(80/90/100%): 유저 알림의 기준 한도는 `cap_u`(`D` 포함). 현행 차감 스크립트는 유저 config가 없으면
  limit 0으로 보고 알림을 내지 않으므로 `D` 적용 유저에 대해 변경 필요(D-10).
- 월 경계: 요청은 **요청 시작 시각(KST)**이 속한 월에 귀속(자정을 넘겨 끝나도 시작 월). 이월 없음 — 매월 사용액 0에서 시작.
  예산 설정값(`T`·`D`·`A_u`·`app_c`)은 월을 넘어 유지되며, 월 중 변경은 **즉시 이번 달 누적 사용액에 대해** 적용된다.
  - 구현 확인 사항: `cost_recorder`가 period을 **요청 시작 시각** 기준으로 계산하는지 검증할 것 —
    응답 완료 시각 기준이면 월 경계를 넘긴 스트리밍 요청이 다음 달 카운터에 들어간다(D-20).

### 6-5. 에러 코드 · 헤더

모든 예산 거부는 HTTP 429, 본문 `{"error": {"type": "budget_exceeded", "code": <code>, "message": ...}}` (현행 형식).

| 단계 | 코드 |
|---|---|
| 0 팀 소속 | `no_team_assigned` (신규) |
| 1 팀 설정 | `team_budget_unset` (현행) |
| 2 유저 (`A_u` 또는 `D`) | `user_budget_exceeded` / `user_soft_limit_exceeded` |
| 3 팀 | `team_budget_exceeded` / `team_soft_limit_exceeded` |
| 4 앱 | `client_budget_exceeded` / `client_soft_limit_exceeded` |

관리 API 거부/경고 코드: `user_not_in_team`, `self_allocation_forbidden`, `user_budget_below_app_cap`,
`app_cap_exceeds_user_budget`, `app_budget_requires_user_budget`, `equal_split_nothing_to_allocate`,
`confirmation_required`, `invalid_amount_precision`.

응답 헤더 (허용된 요청):

| 헤더 | 값 |
|---|---|
| `X-Budget-Remaining` | 모든 계층의 **"차단 시점까지의 잔여"** 중 최솟값. `limit - used`가 아니라 정책 적용 후 실효 한도 기준 (`SOFT_WARNING`은 `1.10×limit - used`. `THROTTLE`은 금액 차단이 없으므로 해당 계층은 최솟값 후보에서 제외) |
| `X-Budget-Tier` | 최솟값을 만든 계층: `user` / `team` / `client` |
| `X-Budget-Limit`, `X-Budget-Used` | 결정 계층이 `user`/`client`일 때만 해당 값. `team`이면 **생략**(팀 정보 비노출) |
| `X-Budget-Warning` | 경고 계층이 있으면 `over_budget` (현행 값 유지) |
| `X-Budget-Warning-Tiers` | 경고 계층 목록, 쉼표 구분 (예: `user,team`) |
| `X-Budget-Throttle` | throttle 활성 시 적용 중인 `throttle_rpm_pct` |

### 6-6. 캐시 모델

- 팀 config 캐시: `T`, 정책, **`D`(`default_user_cap_usd`)**. 미설정 유저의 `cap_u`는 요청 시 팀 config의 `D`로 계산하므로
  **`D` 변경은 팀 config 키 1개 갱신으로 해당 팀 미설정 유저 전원에 반영**된다(멤버 fan-out 불필요).
- 유저 config 캐시: `A_u`, 정책, `app_clients`. 앱 config 캐시: `app_c`, 정책.
- 쓰기 규칙: DB 커밋 후 write-through, 실패 시 해당 키 DEL(콜드 캐시는 DB에서 재수화 — 현행 안전망 유지).
- **staleness 상한: 모든 예산 config 캐시 TTL 300초** (admin-api `BUDGET_CONFIG_CACHE_TTL`과 통일,
  gateway-proxy의 무기한 TTL 변경). 무효화 누락 시에도 최대 300초 후 반영.
- 변경별 갱신 대상:

| 변경 | 갱신 키 |
|---|---|
| `T` / `D` 설정·변경·삭제 | 팀 config |
| `A_u` 설정·변경·삭제 | 해당 유저 config (+ cascade된 앱 config) |
| `app_c` 변경 | 해당 앱 config + 유저 config(`app_clients`) |
| 균등분배 | 팀 config (+ "개별 설정 초기화" 시 대상 유저·앱 config 전부) |
| 팀 이동 | 유저·앱 config (유저의 `team_id` 포함 인증 캐시) |

## 7. 권한 매트릭스

권한은 **admin-api 서버에서 강제**한다(UI 숨김은 보조 수단).

| 작업 | ADMIN | TEAM_LEADER | DEVELOPER |
|---|---|---|---|
| 팀 예산 `T` 설정/수정/삭제 | ✅ | ❌ | ❌ |
| 기본 유저 cap `D` 설정/수정/삭제 | ✅ | ❌ | ❌ |
| 균등분배 (`D` 계산 도우미) | ✅ | ❌ | ❌ |
| 유저 예산 설정/수정 | ✅ 모든 팀 | ✅ 자기 팀, **본인 제외** | ❌ |
| 유저 예산 삭제(→ `D` 적용, 앱 cascade) | ✅ | ✅ 자기 팀, **본인 제외** | ❌ |
| 앱별 예산 설정/수정/삭제 | ✅ | ✅ 자기 팀, **본인 제외** | ❌ |
| 팀 이동 | ✅ | ❌ | ❌ |
| 예산 현황 조회 | ✅ 전체 | ✅ 자기 팀 (`T`, `D`, `team_used`, 초과 약정률, 멤버별 값) | 본인만 (아래) |
| Downgrade 규칙 쓰기 | ✅ | ❌ (§10 유보) | ❌ |

- DEVELOPER 조회 범위: 본인의 `cap_u`와 그 출처(개인 설정 / 팀 기본값), `app_c`(설정 시), 본인 `used_u`·`app_used`,
  본인 기준 실제 사용 가능액(`X-Budget-Remaining`과 동일한 최솟값). `T`, `team_used`, 타인 정보는 **비노출**.
  (사용 가능액이 팀 잔여를 간접적으로 드러낼 수 있으나 UX상 필요한 최소 정보로 수용.)
- **Downgrade 규칙 정의**: 기존 자동 모델 강등 기능(`DowngradePolicy`). TEAM 스코프에서 팀 사용률
  `team_used / T`가 `threshold_pct` 이상이면 요청 모델을 `from_alias → to_alias`로 교체(체인, 동일 provider만 허용).
  `T > 0`이어야 생성 가능. 유저 cap(`A_u`/`D`)은 강등 판정에 영향을 주지 않는다(판정 기준은 팀 사용률만).

## 8. 현행 대비 변경이 필요한 부분 (구현 대상)

| # | 현재 | 변경 | 근거 |
|---|---|---|---|
| D-1 | 리더 경로에만 `ΣA ≤ T` 검증 존재 | **검증 제거**(초과 약정 허용). `set_user_budget`·`allocate`를 공통 검증 함수(I-1~I-4)로 통합 | §2 |

## 9. 운영 시나리오 (수십 명 규모 검증)

`D`(기본 유저 cap)가 있으므로 팀 규모와 무관하게 조작량이 상수입니다. 시나리오별 검증:

| 시나리오 | 관리자 조작 | 비고 |
|---|---|---|
| **팀 신설 / 초기 설정** | `T` 설정 1회 + `D` 설정(또는 균등분배 도우미) 1회 | **전원 cap 적용 완료 — 멤버 수와 무관하게 2회 조작** |
| **일상 운영** | 조작 없음 — 대부분 멤버는 `D`로 커버 | 예외가 필요한 멤버만 개별 `A_u` |
| **예외 조정** | 멤버별 `A_u`/`app_c` 수정 (다이얼로그) | 산발적 — 리더에게 위임 가능(§7) |
| **월 중 `T` 증액** | `T` 수정 1회 | `D`·`A_u`는 자동 유지 |
| **월 중 `T` 감액** | `T` 수정 1회 (+차단 발생 시 확인) | `ΣA ≤ T` 제약이 없으므로 거부 없음 |
| **신규 멤버 합류** | 조작 없음 — 합류 즉시 `D` 적용 | 개별 cap 필요 시에만 `A_u` 설정 |
| **멤버 이탈/팀 이동** | 조작 없음 — §4-5/§4-7 규칙으로 자동 정리 | |
| **정기 점검** | 조회만 — 초과 약정률·사용률·경보 배지 | 알림(80/90/100%)이 능동 통지 |

### 9-1. 수십 명 규모에서 필요한 UI (D-21~23)

- **ADMIN bulk 편집**: 현재 `TeamAllocationView`(멤버별 인라인 입력 + 일괄 Save)는 리더 전용 화면.
  수십 명을 다이얼로그로 한 명씩 열 수 없으므로 admin에게도 팀 단위 bulk 편집 테이블을 제공한다
  (allocate API는 이미 bulk). 개별 다이얼로그는 `app_c`·정책 같은 예외 설정용으로 유지.
- **검색/필터**: 이름·이메일 검색, "미설정(`D` 사용 중)만 보기" 필터 — 대량 멤버에서 대상 식별용.
- **팀 요약 표시**: `D` 값, 초과 약정률 배지, "균등분배" 버튼을 팀 예산 카드 상단에 배치.
- summary 응답은 수십 명 규모에서 무리 없음. 수백 명 이상이면 페이지네이션 검토(§10 유보).

## 10. 유보 사항 (명시적 미결 — 모두 불변식에 영향 없음)

- TEAM_LEADER의 Downgrade 규칙 쓰기 권한 및 `D` 설정 권한: 유보 (현재 ADMIN 전용). 설정값 불변식과 무관.
- 비용 선점 또는 추정 사전 검사(`used + 추정비용 < limit`, `max_tokens` 기준)로 초과 허용 오차 축소: 유보. 사용량 측 개선.
- 초과 약정률 상한(예: `> 2.0`이면 경고/거부): 유보. 현재는 표시만 함.
- 앱 cap을 `D` 사용 유저에게도 허용할지(부모를 `cap_u`로 확장): 유보. 현재는 `A_u` 필수(I-3).
- 다중 팀 소속: 미지원(§1). 도입 시 이 명세 개정 필요.
- 조직/부서 상위 예산 계층: 없음 (필요 시 TEAM 위에 동일 CAP 모델로 추가).
